# Spike report: Go CLI skeleton and release pipeline

[#662 — Spike: Go CLI skeleton and release pipeline](https://github.com/specnaut/specnaut-cli/issues/662),
measured 2026-10-27. The epic it sizes,
[#660 — Rewrite the CLI in Go before Deno runtime support ends](https://github.com/specnaut/specnaut-cli/issues/660),
was put **on hold** the same day while Deno's governance is unclear. Nothing below is a plan to
port: it is what a decision to resume, or to close, would rest on.

## Verdict

The riskiest unknowns hold, with two named gaps, both in the keychain:

| Question                                      | Answer                                                                                                                                                |
| :-------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Does Go reproduce the CLI's argument surface? | Yes. A dedicated tokeniser reproduces `@std/cli parseArgs`; 122 golden command lines generated by the real TypeScript parser agree.                   |
| Embedded templates?                           | Yes, `//go:embed all:templates`, every read through `templates/manifest.json`.                                                                        |
| One command end to end?                       | `reconcile --status`: 0 differences against the TypeScript binary under the parity harness (89 scenarios, 5 ported families).                         |
| Five targets with cgo off?                    | Yes, all five, from one machine.                                                                                                                      |
| Keychain without FFI?                         | Windows: yes, both directions. Linux and macOS: each side works alone, cross-reads fail — see below.                                                  |
| Release shape, no secret?                     | Yes. The dry run produced the eleven asset names and an attestation that `verify-release.ts` accepts for the dry run's identity. No secret was added. |

## Keychain (US5)

Probe matrix: each probe alone (set/get/remove), then each reading what the other wrote. Go uses
`go-keyring` v0.2.8; TypeScript uses the shipped backend port.

| OS                        | Go alone | TS alone | Go reads TS | TS reads Go  |
| :------------------------ | :------- | :------- | :---------- | :----------- |
| Windows (CI)              | match    | match    | match       | match        |
| Linux (CI, gnome-keyring) | match    | match    | **miss**    | **miss**     |
| macOS (maintainer)        | match    | match    | match       | **mismatch** |

- **Linux**: `go-keyring` stores and searches `{service, username}`; the TypeScript backend uses
  `{service, account}`. A port would need its own Secret Service client, or a read-through of the
  old attribute, or every Linux user is logged out at cutover.
- **macOS**: `go-keyring` stores `go-keyring-base64:<…>`; it reads unprefixed values as they are, so
  Go reads TypeScript items, not the reverse. Harmless one way; the port would write the plain value
  (or a downgrade would log users out).
- **Secret off argv**: `go-keyring` hands the secret to `security -i` on stdin
  (`keyring_darwin.go@v0.2.8:86`). Verified from source only: the `sudo eslogger` capture was not
  run, since only the on-hold port depends on it. Linux and Windows: n/a, no child process.
- **Reachability probe**: never throws on any of the three.

### Found on the way: the shipped Windows backend could not store a token

The first Windows run showed the **current** TypeScript backend failing every write and crashing on
a read: its CREDENTIALW offsets were one field late. Filed and fixed independently of any port:
[#671 — Windows keychain backend writes CREDENTIALW at the wrong offsets, so Cloud login cannot store a token](https://github.com/specnaut/specnaut-cli/issues/671).
The second dry run's Windows matrix above is with the fix.

## macOS "Always Allow" across a binary replacement (FR-018, feeds #428)

Observed by the maintainer, 2026-10-27, on an item written by the TypeScript probe (the shipped
backend, Security.framework):

| Read by                  | Prompt?                         |
| :----------------------- | :------------------------------ |
| the binary that wrote it | no                              |
| a rebuilt binary (v2)    | **yes** — answered Always Allow |
| a second rebuild (v3)    | **yes**, despite v2's grant     |
| v2 again                 | no                              |

The grant is bound to the exact unsigned binary, so **every new release re-prompts**: this is
[#428 — Sign + notarize the macOS release binary to stop repeated Keychain prompts](https://github.com/specnaut/specnaut-cli/issues/428)'s
cause, confirmed for the current Deno CLI. A stable code signature is the fix it already proposes.
The Go path (`/usr/bin/security` as the accessing app) was not timed in this session and is not
recorded here.

## Decisions taken by the spike

- **Parser**: no `flag` package and no library — `flag` stops at the first positional and rejects
  unknown flags; the surface is one table plus a tokeniser (`internal/cli/argv.go`).
- **Command**: `reconcile --status` — read-only, no network or keychain, and it exercises the lock
  parser, the staging walk and the refusal preflight.
- **Layering**: `internal/` packages take an `fs.FS` or an `os.Root`; all OS access stays in
  `cmd/specnaut/main.go`. Every later port should keep it.
- **Not portable byte for byte**: an uncaught Deno trace (declared exclusion), JavaScript
  object-model argument shapes (`__proto__`, `_.N`: refused), non-UTF-8 names, `@std/yaml`'s caret
  error text.
- **Target table at cutover**: `scripts/build.ts` `TARGETS` is the one home today; it would move to
  a Go-side table when the Deno tree goes.

## Proposed decomposition, if #660 resumes

Not filed: #660 is on hold, and no port ticket is filed while it is. Sizes are the TypeScript they
replace (handler + use case), a rough guide only.

1. Keychain: a Secret Service client keeping `{service, account}`, plain values on macOS, the #671
   layout on Windows; the harness's credential scenarios on Linux.
2. `diff` and `reconcile <path>` (~400 lines).
3. `check` (~60 + environment probes).
4. `cloud` / `login` / `gate` / `spec` (~820), against the Cloud stub.
5. `self-update` with the Sigstore verifier (~270 + `src/domain/sigstore/`), the riskiest: it is the
   path an installed binary uses to reach the first Go release.
6. `init` (~1000) and `upgrade` (~1660), the largest; the harness's 72-cell matrix is their gate.
7. Cutover: release pipeline on Go, Deno tree and CI removed, version per constitution § XII.

The harness (#661) already covers every row; each port ends at 0 differences for its scenarios.

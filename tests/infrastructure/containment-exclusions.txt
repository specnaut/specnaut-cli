# Modules that mutate the filesystem and are NOT bound by the project-containment
# rule (cli#574). Every line is `<path><whitespace><reason>`, and a reason must
# be a fact about the file — not a date, and not "checked, fine".
#
# The sweep beside this file fails on a mutating module that is neither guarded
# nor listed here. That is the whole point: nine modules mutated the filesystem
# when this rule was written and the first version of the plan hardened two, so
# the rule needed a membership test rather than a longer list.
#
# Before adding a line: the question is not "is this file dangerous" but "does
# it build a path from a PROJECT directory". If it does, guard it.

src/infrastructure/credential_store.ts  writes under the user's own config directory, resolved from the environment and never from a project path — a project cannot influence where it lands
src/infrastructure/github_api.ts  writes beside the RUNNING BINARY during self-update; the path comes from Deno.execPath(), not from any project
src/infrastructure/fs_legacy_migrator.ts  refuses a symlinked .specflow/.specnaut with lstat BEFORE renaming, which is a stronger check than containment: it is the file that CREATES the out-of-project condition rather than one that walks into it

# Per-METHOD exemptions, written `<path>::<method>`. These sit inside modules
# that ARE guarded; the entry says why this particular sink does not carry its
# own `assertInsideProject`.
src/infrastructure/fs_staging_store.ts::delete  removes only the path stagedEntry returned; that helper, which read shares so the two cannot drift apart, ran assertRemovableInProject and assertPlainStagedEntry on that exact entry as its last awaits
src/infrastructure/fs_prune.ts::pruneEmptyParents  asks `locate` whether each folder's real path is strictly inside the real stopAt, and RETURNS instead of throwing — it is a best-effort cleanup walk, and a throw here would fail an upgrade whose files are already written
src/infrastructure/fs_backup.ts::backupAside  a helper whose callers in the bundle and link writers each assert containment on the same path immediately before calling it
src/infrastructure/fs_link_writer.ts::denoSymlink  the default Linker; its only caller, writeContextLink, runs after writeBundle's phase 1 judged the link's own path removable and its target inside the project
src/infrastructure/fs_link_writer.ts::writeContextLink  called only from DenoFsWriter.writeBundle's phase 2 (writeEntry), after phase 1 (assertDestinations) ran assertRemovableInProject and assertLinkTargetInProject on this exact path
src/infrastructure/deno_fs_writer.ts::writeJsonMerge  called only from DenoFsWriter.writeBundle's phase 2 (writeEntry), after phase 1 (assertDestinations) ran assertInsideProject on this exact path
src/infrastructure/deno_fs_writer.ts::writeEntry  DenoFsWriter.writeBundle's phase 2, called only after phase 1 (assertDestinations) ran assertInsideProject, or the two link asserts, on every destination of the bundle
src/infrastructure/deno_fs_writer.ts::writeOwnedFile  called only from writeEntry in writeBundle's phase 2, after phase 1 (assertDestinations) ran assertInsideProject on this exact path; its chmod re-asserts it, since a mode change follows a link created since
src/cli/handlers/init_handler.ts::runInit  its only mutation is the git adapter's ensureDir, which receives the target directory itself rather than a path built under it
src/cli/handlers/verify_scripts_handler.ts::defaultDeps  its only write is the names list, to a fresh file from Deno.makeTempFile in the OS temp directory; no path is built from a project directory
src/infrastructure/fs_tree_export.ts  writes only under the user's cache folder, which stage() refuses when it resolves inside the project; every file and folder it makes is created new under a commit-id-named folder it made itself, so no path is built from a project directory
src/infrastructure/git_branch_fetch.ts::fetch  its only write is the alternates file of the bare repository the export store staged for it in the user's cache folder, outside the project
src/infrastructure/private_folder.ts  its only mutation is a chmod that tightens the user's own cache folder, a path resolved from the environment and never from a project directory
src/infrastructure/fs_export_files.ts  writes only inside the export's seats/ and scratch/ folders, which FsExportStore made new under the user's cache folder; each path is checked strictly inside its copy, and no path is built from a project directory
src/infrastructure/fs_kept_export.ts  removes only `<cache folder>/<full commit id>`, the export fs_tree_export.ts made under the user's cache folder that exportCacheRoot resolves from the environment, after lstat refuses anything but a folder at that name; no path is built from a project directory
src/infrastructure/fs_sandbox_host.ts::removeAll  removes only the scratch folder scratch() made new with makeTempDir in the system temp folder, never a path built from a project directory
src/infrastructure/fs_sandbox_host.ts::reopen  restores the owner's permissions inside that same new scratch folder so it can be removed; it touches nothing outside it
src/infrastructure/sandbox_scratch_volume.ts  makes a new private folder with makeTempDir in the system temp folder for the disk image and removes only that folder; its one other write is a chmod of the run's new scratch folder in the system temp folder, once the image is mounted on it; no path is built from a project directory
src/infrastructure/session_record_files.ts  writes only in the session record folder `FsSessionRecords` opens under the repository's own git directory, as `git rev-parse --absolute-git-dir` names it, never a path built from the work tree: the record created new beside its name and hard-linked onto it, other sessions' records unused past the retention removed from that folder only, and a record's times renewed when used, the folder's `specnaut/` and `session/` refused as a link before a write, a resume or a renewal
src/infrastructure/sandbox_seatbelt_runner.ts::run  creates only the policy's write folders, which the policy places under the run's new scratch folder in the system temp folder, never under a project directory
src/infrastructure/fs_review_pass.ts  writes only under the repository's own git directory, as `git rev-parse --absolute-git-dir` names it, never a path built from the work tree: in `specnaut/` there, whose folder is lstat'ed and refused as a link, the pass created new beside its name and renamed onto it, and removed by its exact path when revoked or taken
src/infrastructure/fs_review_lock.ts::lock  writes only the session's lock entry under the repository's own git directory (`git rev-parse --absolute-git-dir`, in `specnaut/review-lock/`) and under the user's state folder (`$XDG_STATE_HOME`, else `~/.local/state`, in `specnaut/review-lock/`), never a path built from the work tree; both folders are checked as real folders, not links, before the entry is made
src/infrastructure/fs_review_lock.ts::createEntry  creates the entry new (createNew, mode 0600) at the path lock() built in those two folders; an entry already there is left as it is
src/infrastructure/sandbox_bwrap_runner.ts::scoped  makes a new private folder with makeTempDir in the system temp folder for the scope's start marker, and removes only that folder, never a path built from a project directory
src/infrastructure/sandbox_engine_env.ts::engineRunEnv  writes only a containers.conf, an empty mounts.conf and an empty hooks folder inside a new folder made with makeTempDir in the system temp folder, and removes only that folder, never a path built from a project directory
